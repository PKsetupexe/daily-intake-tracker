# 每日摄入（3.6.0）

本地饮食、营养、运动和体重记录应用。完整功能以 Electron 桌面版为准；支持 Windows，macOS 移植源码与自动打包流程见 [Mac 接力说明](docs/MACOS.md)。网页开发服务和仓库中的旧版 VBS/Python 启动器不等同于桌面版。

## 源码与隐私

仓库保存源码、测试、图标、构建配置、依赖锁定文件，以及可公开分发的食品和运动预置数据（`electron/starter-catalog-data.mjs`，安装包镜像位于 `installer/electron-app/`）。不保存 API Key、外部接口令牌、个人饮食或运动记录、SQLite 数据库、云盘同步包、编译目录和安装包。桌面版将个人数据库保存在 Electron 的用户数据目录下的 `data/food_manage.sqlite`；项目根目录的 `data/` 属于旧版 Python 服务，两个目录都不应提交。

在新电脑安装 Git、Node.js 22.13 或更新版本与 pnpm，然后执行：

```powershell
git clone https://github.com/PKsetupexe/daily-intake-tracker.git
cd daily-intake-tracker
pnpm install --frozen-lockfile
pnpm test
```

网页界面开发使用 `pnpm dev`。桌面主进程源码位于 `electron/`，`installer/electron-app/` 是打包用的同名模块镜像及 Electron Builder 配置。生成桌面安装包前，运行 `pnpm build` 和 `pnpm desktop:prepare`，再运行 Electron Builder。构建产物只在本地生成，不进入仓库。新电脑首次启动后，需要在应用设置中重新填写 API Key 和本机云盘同步路径；历史数据通过应用的云盘完整快照与后续增量恢复。

## 浅色与深色模式

应用默认跟随系统的浅色或深色外观，也可以在顶部“外观”设置中固定使用浅色或深色。首页、历史统计、设置、对话框、表单和弹窗均使用对应主题。图表数据点的悬停信息由应用自行绘制，因此两种模式下都能保持清晰可读。外观偏好只保存在当前电脑，不进入数据库、云盘同步包或安装包。

界面中的说明、按钮、状态和营养明细设置了适合笔记本及高分屏阅读的字号下限；图表坐标与数据标签也单独提高了字号。

首页日期只允许在“日期”和“星期”之间换行，不会拆散日期或星期文字。营养素总览会直接显示全部维生素与矿物质；每日目标计划默认折叠，需要时再展开修改。历史页优先显示趋势与每日汇总，历史分析随后展示，同步和备份设置统一放在页面底部。

居家久坐基线系数按日期保存历史。修改滑块或精确值时会记录所选日期、系数和记录时间；历史热量与三大营养素参考线会采用对应日期最近一次生效的系数。系数历史属于正式用户数据，会进入增量同步包、完整快照、云端恢复和手动备份。

应用也支持保存生日、生理性别、身高和体重历史。体重会显示为趋势曲线，并用于基础代谢与运动热量估算。

## 打开应用

安装 Electron 版后，从 Windows 桌面快捷方式或 macOS“应用程序”打开“每日摄入”。应用会自动启动本地数据库和界面，并在独立桌面窗口中打开。

项目根目录中的 `启动每日摄入.cmd` 和 `DailyIntake.vbs` 属于旧版 Python/Edge 启动方式，不包含新版桌面功能。

## 数据存放

桌面版的饮食和运动记录保存在本机 SQLite 数据库中；只有主动开启云盘同步后，记录才会进入所选同步目录。网页开发服务与旧启动器使用项目根目录的另一份数据库，不应与桌面版混用。

- 使用安装后的桌面应用打开完整版本。
- 桌面版数据库位于 Electron 用户数据目录下的 `data/food_manage.sqlite`；旧版 Python 数据库位于项目的 `data/food_manage.sqlite`。
- 在“历史与备份”页面定期点击“下载备份”。
- 个人资料和体重记录会一起包含在备份中。
- 更换浏览器或清理浏览器数据前，先下载 JSON 备份，之后可重新导入。

## 云盘同步

在“历史、同步与备份”中可以选择“仅本地使用”或“开启同步”。开启后，每台电脑仍使用自己的本地 SQLite 数据库，云盘目录只保存可合并的增量记录包与定期完整备份。

- Windows 自动检测账户的 OneDrive；macOS 会查找现有的 `~/Library/CloudStorage/OneDrive-*` 目录，并建议使用其中的“每日摄入同步”子文件夹。
- 可以直接输入或浏览选择 Dropbox、坚果云等其他网盘的本地同步目录。
- 每 60 秒检查一次增量，每 24 小时创建并校验一次完整备份。
- 每 24 小时还会创建一个包含删除状态、记录更新时间和已覆盖事件 ID 的可迁移完整快照；新电脑会先读取快照，再合并剩余增量。
- 历史增量只有在超过 90 天、已被最新校验快照覆盖，并且删除后仍至少保留 500 个增量文件时才会自动清理。
- 历史完整备份至少保留最近 7 份，迁移快照至少保留最近 3 份，避免云盘文件无限增长。
- “导出全部记录到云盘”可立即生成并校验完整快照；“同步云端全部数据”可在新电脑上主动读取全部快照和剩余增量。
- API 密钥、外部接口令牌、LLM 设置与聊天记录不会写入同步目录或完整备份。

## 趋势统计

历史页面包含两张可交互趋势图：

- 能量图以净摄入（摄入减运动）和负向运动消耗为两个数据点，两线之间的半透明面积代表摄入热量。
- 净摄入参考线会按每一天的趋势体重和热量盈余/缺口计划动态变化，不再是一条固定横线。
- 营养图同时显示蛋白质、碳水和脂肪，采用兼顾色觉差异的蓝、橙、洋红配色；实际摄入均为醒目实线并辅以不同点形，参考目标为浅色细虚线。
- 三种营养素的实际摄入线和动态参考线都可分别显示或隐藏。
- 蛋白质、碳水和脂肪的参考点分别沿用圆形、方形和菱形；参考线向下带有浅色渐变。渐变会按每个日期区间的参考线高低顺序切分，上层渐变到达下一条参考线前归零，不会与下层颜色叠加混色。
- 时间范围可选 7 天、14 天、月、季度、年度或全部数据；数据点可选每天、每周平均或每月平均。
- 周平均与月平均只计算有记录的日期，不会把漏记日期当成零。
- 体重趋势图也支持同一组时间范围和每天、每周平均、每月平均数据点。

## 每日目标计划

首页可以选择日常、无氧健身日或有氧训练日情景，并可选择是否设置每日热量缺口或盈余。今日和历史日期的热量、蛋白质、碳水与脂肪参考目标会同时更新。

两次体重记录之间按日期线性插值；最后一次体重记录之后沿用最近体重。因此查看往期日期时，目标会按当时的趋势体重计算，而不是统一使用现在的体重。

热量目标按整数千卡计算，不做 50 千卡级别的粗粒度取整，因此小幅体重变化也能反映到参考目标中。

热量口径采用“居家久坐基线 + 净活动热量”：净摄入目标以 Mifflin–St Jeor 静息代谢估算乘以 1.2 为基础，代表整天在家打游戏、看电视，仅有最低生活活动的情形。走路、通勤、家务和训练应记录高于静息状态的净活动热量。手表数据应填写“活动热量”或“运动热量”，不要填写包含静息代谢的全天总消耗。

“每日目标计划”提供红色到绿色的基线系数滑块：左侧表示较低消耗、易胖倾向，右侧表示较高消耗、易瘦倾向，默认值为 1.20。滑块范围为 0.70–2.00，并保留精确数值输入，可依据外部估算或至少数周的体重趋势校准；该系数会同步影响首页和历史参考线。

## 自然语言与语音

首页提供真正的 LLM 对话录入。点击“配置 LLM”，可设置 OpenAI 兼容接口地址、模型、API Key、联网搜索开关和系统级提示词。API Key 只保存在本机共享数据库。

系统提示词要求模型返回经过约束的 JSON 操作；本地服务校验后才会写入饮食、运动、体重或个人资料。

Qwen Chat Completions 联网时会发送 `enable_search: true`。应用内浏览器可能不支持网页语音识别；Chrome 或 Edge 的支持情况取决于浏览器和麦克风权限。

## 外部写入 API

“LLM 与外部 API”设置窗口会显示本机写入地址和 Bearer Token。外部代理可提交：

```json
{
  "actions": [
    {
      "store": "foods",
      "value": {
        "id": "unique-id",
        "date": "2026-07-26",
        "time": "12:00",
        "meal": "午餐",
        "name": "食物名称",
        "weight": 100,
        "note": "数据来源",
        "calories": 0,
        "protein": 0,
        "carbs": 0,
        "fat": 0
      }
    }
  ]
}
```

请求头必须包含 `Authorization: Bearer <Token>`。完整食物记录应提供应用支持的全部营养字段，缺失数值会按 0 处理。

## 3.0.0：食品库与快捷记录

桌面安装包新增 `foodLibrary` 记录类型，保存在原 SQLite 的统一 `records` 表内，与饮食记录使用同一套同步引擎，无需维护第二个数据库文件。

- 首页提供“手动添加”和“选择已记录过的食物”。选择食品并填写克重后，全部营养值按比例即时更新，保存为独立饮食记录。
- 历史页在营养趋势下方、每日汇总上方提供食品库。支持新增、修改、删除、名称/备注搜索，复用每日汇总的分页控件。
- 排序支持字母/汉字拼音、初次记录时间、最近修改时间、每百克热量、每百克蛋白质，均支持正序与倒序，搜索结果采用相同排序。
- 每次桌面启动检查缺失食品，导入与同步后也会补齐。换算公式为 `营养值 × 100 ÷ 克重`，保留计算精度，仅显示时取小数，不调用 LLM。零、负数、缺失或非有限克重不能换算，原饮食记录仍保留。
- 名称经全半角、大小写和空格规范化后去重；不自动合并不同名称、品牌或烹饪方式。同名旧记录按最近有效修改记录取营养值，初次时间取最早可追溯记录时间。旧数据没有真实创建时间时使用饮食日期与时间；已有食品不会被日常饮食自动覆盖，可在食品库手动修正。
- 修改食品库不追溯修改历史饮食。删除和改名后，旧记录不会再次自动生成原食品；可通过新增食品显式恢复。
- 食品库复用增量事件、冲突处理、OneDrive 文件同步、完整快照、手动备份与保留清理策略。没有新增另一套碎片文件机制，反复启动不会重复生成事件。
- 多设备请全部升级到 3.0.0 再使用食品库；旧版不认识新增记录类型。此版本交付以 Electron 安装包为准，旧 `DailyIntake.vbs` / Python 网页启动器不提供新食品库及完整桌面同步功能。

构建安装包时，先运行 `pnpm build` 和 `pnpm desktop:prepare`，再执行 Electron Builder。安装包不包含个人数据库、API 密钥或测试数据。

## 3.0.1：食品名称清洗

食品名称不再包含括号内的份量、克重、去皮或配料说明；这些内容追加到已有 `note` 字段。品牌、品种和区分食品身份的烹饪方式保留。常见写法如“白米饭 (300g)”“白米饭 (360g)”共用一个食品库条目。

新记录在写入前执行确定性名称整理，默认 AI 提示词和每次请求附加的强制规则同时要求名称与备注分开。饮食营养字段仍保存本次份量的总值，食品库才是每 100 g 数据。原有备注不会被覆盖。

启动及导入同步后会整理旧名称、合并重复食品库，并通过原同步引擎传播更新和删除标记。清洗作为原子批量操作执行；食品库重复项采用最近修改版本的每百克营养值并保留最早创建时间，饮食记录的 ID、日期、克重及营养字段全部保持不变。其他设备首次自动清洗前，会在本机数据目录保存 `before-food-name-cleanup-v1.json` 备份。已删除食品不会因旧别名再次自动出现。

## 3.1.0：运动库与独立步行费率

运动记录自动按每 10 分钟归一化，名称保留强度、配速和速度，MET 估算依据放入备注，时长移入备注；男、女和未注明性别分别保存。首页可手动添加运动或从运动库按时长快速添加。历史页提供搜索、拼音/初次记录/最近修改/耗能排序、正倒序、分页和增删改。删除库条目不删除历史运动。

步行独立按每 1000 步管理。自动模式采用「体重（kg）× 0.35 kcal / 1000 步」，以平地净耗能约 0.5 kcal/kg/km、平均步长 0.7 米简化估算；依据为 [ACSM 步行耗氧公式](https://pmc.ncbi.nlm.nih.gov/articles/PMC11462406/)，并非针对个人实测。体重变化更新自动费率，历史耗能保持原值。手动模式锁定用户数值（包括 0），体重和 AI 不得覆盖；仅手动值留空时允许 AI 首次估算，自动提取每千步费率并锁定。AI 即使使用自定义提示词，也会接收这些规则和当前费率。

新版首次启动先备份，再整理旧运动名称并补齐运动库；不会改动历史热量、时长或步数。运动库和步行设置使用现有 OneDrive 增量、完整快照、删除标记、备份恢复和碎片清理机制。多设备应全部升级至 3.1.0。其他运动的费率由实际记录或手动编辑更新，不随体重自动变化。


## 3.2.0：常见食品与运动预置、名称清洗

安装包内置29种食品和56条运动（男女各28条）公共参考数据。首次启动自动补齐，已有同名条目优先；用户修改、删除后不会被预置数据覆盖或复活。预置同步事件采用稳定标识与低优先级，首次启用/切换OneDrive目录也保留这一优先级，复用现有快照、备份与碎片清理机制。

食品采用USDA SR Legacy 2018每100g可食部数据，覆盖米饭、意大利面、蛋奶、蔬果、肉类和饮料。原料标题区分生熟、带皮或去皮，近似部位与品牌地区均在备注明确说明。双吉预置为USDA美版参考，备注记载同一来源标准份量1个=155g，并非中国门店统一重量。未报告营养字段显示“未报告”，统计时不计入，不等于实测为零。用户可修改或补充。

运动参考2024 Adult Compendium。男条目参考70kg，女条目参考60kg；相同活动使用相同代谢当量，差值来自参考体重，不是固定性别系数。每10分钟净耗能=(代谢当量−1)×3.5×参考体重÷200×10。配速7分/公里条目为相邻档位近似插值，其余在备注列明档位。既有运动库仍保持用户实际记录，其他运动不随体重自动更新。

同一强度的健身房力量训练、无氧力量训练、抗阻训练统一为力量训练；不同模型MET估算不再拆成多个运动，依据保留在备注。合并库条目采用最新修改值，同一迁移时间则优先最近运动来源，保留最早创建时间与各来源备注。历史运动只整理名称和备注，不合并不同日期的真实记录，不修改热量、时长或步数；删除标记同步至其他设备。

食品命名和AI提示词保留影响每100g营养的配方与做法，包括少油、减油、减糖、去酱、去皮等；份量、每个克重与来源版本写入备注。旧“名称补充”中明确保留的做法也会恢复到标题。AI可读取食品库营养、份量备注和版本，不跨地区混用份重。

参考数据来源：
- https://fdc.nal.usda.gov/download-datasets/ （数据记录链接在每条食品备注）
- https://pacompendium.com/adult-compendium/ （活动分类和代码在每条运动备注）
- https://www.mcdonalds.com.cn/product/double-cheeseburger （中国版每个营养，未混用于美版每100g数据）

复现预置数据：运行 `python scripts/build-starter-catalog.py`，首次会下载官方SR Legacy公开CSV数据至忽略的work目录；生成的公共参考模块可随源码分发。个人数据库、演练备份和测试配置不会打包。


## 3.3.0：AI批量记录与默认份量
AI同一消息中的多道食物、多项运动分别写入；兼容同一store的value数组，规范“1小时”“半小时”等时长和含逗号的步数。新增记录由软件分配独立ID，避免模型复用ID覆盖前一条；修改仍通过原ID与update操作定位。所有动作和聊天保存使用同一事务，任何一条校验失败都会回滚整批；食品/运动库扫描及同步发布在批次末执行。失败时首页保留原输入并显示具体原因。实际模型可能仍有理解偏差，记录后可在首页核对各项。
食品库新增defaultServingGrams默认份量字段，始终与每100g营养基准分离。选择食品时自动预填该克重，历史与备份页可编辑。新饮食写入会更新对应默认份量；手动设置不会被已有旧记录反复覆盖。首次升级先备份：没有字段的食品优先取最新摄入日期/时间的有效克重，没有摄入历史时取同版本备注单份克重，再按常见单人份估测并注明可修改。克重、来源、更新标记参与现有OneDrive同步和备份，预置迁移保持低优先级，不覆盖其他设备的用户修改。历史营养、食品库每百克营养和既有摄入数值保持不变。


### 3.4.0 通讯录选择与近期趋势
食品和运动选择弹窗改为按字母/拼音分组的滚动通讯录，含数字与特殊符号组；不再分页。默认字母排序，可切换实际记录日期倒序，未使用的预置条目排在后面。手动置顶最多5项，自动补入最多3个最近使用项，总置顶不超过5项。搜索保留排序及置顶规则，填写区在所选卡片内部展开，标题及提交操作固定。本机排序与置顶保存在SQLite settings，不随临时页面端口变化；运动按性别分别保存。净摄入/运动消耗、三大营养素两图在打开或更换时间范围、数据粒度时定位最新日期，保留向左查看旧数据的能力。
验证：node --test tests/*.test.mjs；scripts/smoke-directory.mjs 和 scripts/smoke-directory-restart.mjs 使用隔离数据检查桌面及跨进程偏好。


### 3.5.0 编辑记录与比例挂钩
首页饮食编辑默认将重量与全部营养挂钩，营养输入只读；脱钩可独立填写，重新挂钩以当前填写值为比例基准。显式编辑饮食时比较每100g比例，等比例改重量仅更新默认份量；比例改变同步更新食品库，改名同步处理名称，仍被其他历史记录引用的旧条目保留。记录与食品库修改在同一同步事务内完成，保留用户已删除的食品库条目。活动卡片新增修改：步行按步数、其他运动按时长默认挂钩，脱钩可独立填热量；步行修正只影响本条记录，不更改全局步行费率。旧记录缺少有效重量/步数/时长时先补数值再挂钩。验证包含同步回滚和隔离桌面脚本 scripts/smoke-linked-edit.mjs。

### 3.6.0 模型代理与请求头
模型请求使用独立的 Electron 网络会话：自动跟随系统代理，代理连接拒绝时仅回退直连一次；可选择强制直连、仅系统代理或自定义 HTTP/HTTPS/SOCKS5 代理。不会探测 Clash 进程或硬编码端口，不使用陈旧的 HTTP_PROXY/HTTPS_PROXY 环境变量。TUN/VPN 系统路由由操作系统决定。HTTP 错误不会自动重发，避免重复模型调用；上游转发服务自身的代理错误会明确提示。
请求头预设包含自动识别、标准兼容和 OpenCode。OpenCode 自动附加持久会话 x-opencode-session 和真实客户端 User-Agent，录入和不同范围的分析分别管理会话；清空会话更新 ID。支持本机自定义 JSON 请求头，禁止换行及连接控制头，不进入云盘同步。地址支持基础路径或完整 chat/completions 路径；Qwen 专用 enable_search 仅发送给阿里云接口。
OpenCode Go 官方面向编程代理，营养助手是否符合服务用途由提供方决定：https://opencode.ai/docs/go/#where-can-i-use-it 。不伪装其他客户端。
验证：tests/model-network.test.mjs；scripts/smoke-model-network.mjs 使用真实 Electron 请求和本地代理模拟系统代理关闭、失效及启用；scripts/smoke-batch-servings.mjs 验证会话头、清空重置及原有 AI 写入功能。未使用真实付费 API 进行验证。

### 3.7.0 营养近期视图
首页“不只看热量”标题右侧新增默认开启的近期视图开关，关闭恢复原有数字与进度条。各营养素使用当前所选日期及之前最近30个有饮食记录日期，按日汇总；不足30个点保持1/30间距靠右，不为缺失日期补零。钠、添加糖按上限判色，并在参考虚线上方绘制向上淡出的斜纹；其余有参考值的营养素达标绿、未达标红；纯统计项首尾上升红、下降绿、持平灰。虚线跟随实线颜色，右侧参考值使用同色实心标签，无建议量显示“仅统计”。所选日期无记录时标明未记录，参考类使用中性色。深色主题摄入值白字，浅色主题深色字。鼠标停留数据点可看日期与数值，底部显示实际记录区间。
验证：tests/nutrient-recent.test.mjs 与 scripts/smoke-nutrient-recent.mjs；明暗主题截图在隔离 smoke-profile-nutrient 目录，不包含个人数据。
